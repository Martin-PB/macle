# Study — Provenance, temporal relations, and event envelopes

**Status:** standards and literature survey, 13 November 2026.  
**Decision status:** no standard or serialization adopted.  
**Question:** which existing standards or formalisms could support MACLE's provenance, temporal reasoning, and event exchange without being mistaken for the whole domain model?

## 1. The problem has distinct layers

MACLE has at least three related but different needs:

1. **Provenance semantics:** explain which source entities, processing activities, agents, and derivations support an observation.
2. **Temporal semantics:** represent points, intervals, uncertainty, overlap, ordering, and multiple clock domains.
3. **Event exchange:** transport an event or observation between components with stable identity and enough context for routing and interpretation.

No single candidate below solves all three. They should be evaluated as complementary layers, not competing whole-system architectures.

## 2. W3C PROV-O / PROV-DM — provenance model

### What it provides

W3C PROV is a family of specifications for interoperable provenance. PROV-O is an OWL 2 ontology mapping the PROV data model into RDF.

Its three central classes are:
- **Entity:** a physical, digital, conceptual, or other thing with fixed aspects.
- **Activity:** something occurring over time that uses or transforms entities and may generate entities.
- **Agent:** something bearing responsibility for an activity, entity, or another agent's activity.

Important relations include:
- an activity used an entity;
- an entity was generated by an activity;
- an entity was derived from another entity;
- an activity was associated with an agent;
- an entity was attributed to an agent;
- one activity was informed by another.

Qualified relations can carry additional details such as roles, times, and responsibility.

### MACLE relevance

A possible provenance chain can be represented as:

source audio artifact → capture activity → media segment → speech extraction activity → transcript segment → diarization activity → speaker hypothesis

The source artifact, intermediate segments, and derived outputs are entities; capture and extraction executions are activities; software, organizations, or human annotators may be agents.

PROV offers a vocabulary for provenance relations without requiring MACLE's entire domain ontology to be expressed as PROV classes. It could be used as a mapping or export vocabulary.

### Limitations and questions

- PROV does not define MACLE's meeting ontology, participant/endpoint/session semantics, evidence epistemology, or uncertainty model.
- It does not by itself define the complete meaning of a speech segment, platform event, speaker hypothesis, or contradiction.
- Mapping every MACLE concept directly to PROV-O may create an awkward model if provenance concepts are treated as the primary domain types.
- The project must determine whether to use PROV terms natively, map a MACLE model to PROV, or support a partial interoperable export.

**Preliminary assessment:** strong candidate for provenance interoperability and lineage, not a complete MACLE domain model.

## 3. Allen's interval algebra — temporal relations

### What it provides

James F. Allen's 1983 work, “Maintaining Knowledge about Temporal Intervals”, introduces an interval-based temporal representation and a constraint-propagation approach to reasoning about relations between intervals.

The familiar interval relations include:
- before / after;
- meets / met-by;
- overlaps / overlapped-by;
- starts / started-by;
- during / contains;
- finishes / finished-by;
- equals.

The framework is useful when the question concerns how two time intervals relate, rather than merely comparing their start timestamps.

### MACLE relevance

Examples:
- a chat message occurs during a screen-share interval;
- two speech segments overlap;
- a participant session starts before a capture session and ends after it;
- a screen-share change meets or overlaps a spoken explanation;
- a capture gap contains a period in which no platform event was observed.

Interval relations could support temporal competency questions and consistency checks across modalities.

### Limitations and questions

- Allen relations assume intervals with sufficiently defined endpoints; MACLE may have uncertain endpoints, missing timestamps, clock skew, and source-specific time bases.
- A relation inferred from uncertain timestamps should carry the assumptions and precision that support it.
- Allen's algebra does not replace a timestamp representation, clock-synchronization model, or event identity model.
- Constraint propagation can produce multiple possible relations; MACLE should not force a single relation where evidence is insufficient.
- Point events may need explicit representation or conversion to intervals under a documented convention.

**Preliminary assessment:** strong candidate for temporal relation vocabulary and reasoning, subject to uncertainty-aware extensions.

## 4. CloudEvents — event context and transport

### What it provides

CloudEvents is a vendor-neutral specification for describing event data in a common way across services, platforms, and systems. The core specification version listed by the project is 1.0.2.

Required context attributes include:
- **id:** event identifier, unique in combination with source for each distinct event;
- **source:** URI-reference identifying the event context/source;
- **specversion:** CloudEvents specification version;
- **type:** event type.

Optional context attributes include:
- **subject:** subject within the source context;
- **time:** occurrence time, when available;
- **datacontenttype:** data content type;
- **dataschema:** URI identifying the schema for the data.

Extension attributes can add producer-defined metadata. The event data remains domain-specific payload.

CloudEvents recommends keeping event context compact and avoiding sensitive information in context attributes. Large or sensitive payloads can be referenced or protected separately, with appropriate access controls and encryption.

### MACLE relevance

CloudEvents could be useful for distributing normalized MACLE events between capture adapters, processing components, storage/indexing services, and consumers.

It offers a common transport envelope with source-scoped identity and event type while leaving the payload schema to MACLE.

### Limitations and questions

- CloudEvents is an event envelope and interoperability format, not a domain ontology or provenance model.
- Its optional time attribute is not a complete multi-clock model. MACLE still needs to distinguish valid/event time, observation time, ingestion time, and processing time.
- It does not define the meaning of platform participant, endpoint, person hypothesis, speaker segment, evidence class, confidence, or contradiction.
- Its type and extension conventions do not replace versioning and governance of MACLE's own domain vocabulary.
- Event delivery, ordering, persistence, deduplication, replay, and exactly-once processing are not guaranteed merely by adopting CloudEvents.

**Preliminary assessment:** plausible event-exchange format if MACLE later exposes event streams; not a canonical observation or domain model by itself.

## 5. Comparison

| Need | PROV-O / PROV-DM | Allen interval algebra | CloudEvents |
|---|---|---|---|
| Source/derivation lineage | Core purpose | No | Limited source/event context only |
| Processing activity and responsible agent | Core vocabulary | No | Producer context only |
| Entity-to-entity derivation | Core vocabulary | No | No |
| Temporal interval relations | Not its main purpose | Core purpose | No |
| Clock domains and timestamp uncertainty | Requires additional modeling | Requires additional modeling | Not provided by core envelope |
| Event identity and source | Not a transport envelope | No | Core purpose |
| Event type and payload transport | No | No | Core purpose |
| Meeting/person/endpoint ontology | Must be supplied by application | No | Must be supplied by payload/domain |
| Epistemic status and confidence | Requires application extension | No | Requires application payload/extensions |

## 6. A possible layered use — hypothesis only

A future MACLE design could use:
- a MACLE-owned domain model for meeting situations, identities, observations, events, relations, and evidence;
- PROV-compatible provenance relations for source and derivation lineage;
- Allen-inspired temporal relations for interval reasoning;
- CloudEvents for optional event distribution between components.

This is not an adopted architecture. The conceptual model should remain understandable without requiring RDF, OWL, CloudEvents, or a specific event broker.

The key test is whether the mapping preserves meaning without loss:
- Can every source assertion and transformation be traced?
- Can uncertain time relations remain uncertain?
- Can event transport preserve original platform source identity?
- Can consumers interpret a MACLE event without depending on a vendor-specific payload?
- Can the same domain model be represented without choosing a transport protocol?

## 8. No decision made

No standard is adopted as MACLE's canonical representation, serialization, provenance store, temporal logic, or event transport. The next step is to test these candidate mappings against the competency questions and the proposed domain model, including a small worked provenance-and-time example.
